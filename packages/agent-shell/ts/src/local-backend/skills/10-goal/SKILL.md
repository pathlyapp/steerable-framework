# 目标跟踪（Goal）

用户希望这次不是随手做一件事，而是**盯住一个目标直到真正达成**。本技能的顺序是固定的：先立目标 → 落成清单 → 执行并更新 → 逐条验收。

## 1. 先立目标（不要跳过）

开工前，用不超过 6 行把目标说清楚：

- **目标**：一句话描述「做完之后世界变成什么样」，必须是结果，不是动作。
  - ✅ 「本地能一条命令跑通测试并全绿」
  - ❌ 「去看看测试」
- **验收标准**：2-4 条可检验的条件，每条都要能用一次工具调用或一段真实输出来证明。
- **不做什么**：明确本次不处理的范围，避免越做越大。

信息不足时，**先问最关键的 1-3 个问题再动手**，不要靠猜设定验收标准。用户已经给足信息时不要明知故问。

## 2. 落成清单（todo_write）

目标确认后立刻调 `todo_write` 建清单：

- 每条对应一个可独立验证的步骤，通常 3-8 条；一步就能做完的事不用本技能。
- 步骤顺序即执行顺序；有依赖关系的写在后面。
- 验收标准本身也要有对应条目（例如「跑一次测试确认全绿」），否则收尾时没有证据。

## 3. 执行并更新状态

- 开始某条 → 标 `in_progress`，**同时只能有一条**。
- 某条做完 → 立刻标 `completed`，不要攒到最后一起改。
- 范围变化（发现某步不必做、或必须新增一步）→ **重写清单**并用一句话说明为什么变，不要偷偷跳过。
- 清单还有未完成项时，**不允许**用纯文本汇报进度然后停手。

## 4. 收尾验收

所有条目完成后，按验收标准逐条给结论，每条都要带**真实证据**（工具返回的输出、文件路径、退出码、页面变化），不要只写「已完成」。

格式：

```
目标：<一句话>
- [x] 验收1：<结论> —— 证据：<真实输出摘要 / 文件路径>
- [x] 验收2：<结论> —— 证据：<...>
- [ ] 验收3：未达成 —— 原因：<真实原因>，建议：<下一步>
```

有未达成项时**如实列出**并给出下一步，不要为了收尾而宣称成功。

## 与其他机制的关系

- 目标很大、可以并行或上下文很重 → 子任务用 `delegate_subagent` 委派，跨回合的长任务用 `task_run`（有先后关系用 `dependsOn` 串起来），主线仍然靠本清单跟踪。
- 用户只想先看方案、暂时不执行 → 让他切到输入框底部的 **Plan 模式**，那里会产出可确认的计划；本技能负责的是「认领目标并做完」。
